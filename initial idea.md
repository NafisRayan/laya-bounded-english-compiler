## Design Rationale, Alternatives Considered, and Full Workflow

In designing this system, we did not begin with the assumption that a single model or a single generation strategy would be sufficient. We evaluated several candidate architectures before arriving at the layered, deterministic backend-compiler design. The alternatives fell into five broad categories.

**End-to-end LLM generation.** The most obvious approach was to let a large language model read the user’s natural-language description and directly generate Supabase SQL migrations, RLS policies, and configuration. We rejected this because it is nondeterministic: the same prompt can produce different schemas, the model can hallucinate tables or policies that do not exist, and there is no reliable way to audit or reproduce a build. It is also expensive and slow per request, and it offers no principled way to flag unsupported requirements. A malformed RLS policy generated by an LLM is a security risk, not just a bug.

**Laya as a zero-shot extractor.** We considered using Laya to “extract” entities, roles, relationships, and features directly from free text. This was rejected because Laya is a non-autoregressive decision engine, not a generative extractor. It scores typed choice, score, and yes/no questions against options supplied at inference time. It cannot invent a label such as `photography_equipment` if that label is not in its option set, and its base checkpoints are near random on typed-decision benchmarks. Treating Laya as an extractor would produce silent failures: the closest available option would win by default, and the user would never know a requirement was missed.

**Pure rule-based or keyword parsing.** We also considered a deterministic parser using aliases, keyword mappings, and phrase rules. While this avoids hallucination, it is brittle. A user who writes “renters need to reach out to owners before committing” does not use the word “message,” yet the system must infer `messaging = true`. Expanding the alias dictionary is combinatorial and endless, and the failure mode is silent omission: the requirement never enters the specification, and the generated backend is missing a feature the user asked for. We therefore kept deterministic rules as a first pass but not as the sole interpreter.

**Direct text-to-SQL or schema generators.** Existing tools such as DbSmash and Supabase schema generators use LLMs to produce schemas from plain English. These are useful prototypes, but they are one-shot, non-interactive, and not built around a validated intermediate specification. They do not provide a structured blueprint the user can review before deployment, and they do not handle ambiguity through guided clarification. We rejected this as the core architecture because it lacks the specification layer that makes correctness auditable.

**Laya with a very large vocabulary.** We considered simply expanding Laya’s option set to cover every possible entity, feature, and integration. This fails for three reasons: Laya’s choice questions are recommended to stay under twenty options; accuracy degrades as the label space grows; and the context window limits how much state Laya can score at once. A large vocabulary also reintroduces the same silent-omission risk because unsupported labels cannot be generated.

We ended up with a layered architecture because each layer addresses a specific failure mode. Laya classifies against a fixed, domain-agnostic ontology so it never has to invent a label. The ontology bounds what the system can generate, so unsupported requirements are flagged rather than guessed. The MCQ engine resolves ambiguity using only capabilities the platform knows how to build. The Backend Specification is the intermediate representation that makes the build inspectable and versioned. The deterministic generator compiles that specification into pre-tested SQL and configuration fragments, eliminating nondeterminism and hallucination from the generation loop. Supabase provides the execution layer because its Management API and CLI allow fully programmatic project creation, migration, and configuration.

The full workflow is as follows. The user describes the backend in natural language. A Requirement Interpreter combines exact mappings, alias and phrase rules, Laya classification over the ontology, candidate generation, confidence scoring, and contradiction detection. High-confidence decisions are auto-accepted; low-confidence or contradictory decisions are marked ambiguous; requirements that match no ontology item are marked unsupported. Ambiguous decisions trigger adaptive MCQs generated from a dependency graph, so the user is only asked questions that are relevant to the current partial specification. Each answer fills in another part of the Backend Specification. Once the specification is complete, a validator checks dependencies, type consistency, role permissions, and contradictions. The user reviews a visual blueprint and approves or edits it. A deterministic generator then composes pre-tested fragments into SQL migrations, RLS policies, auth configuration, storage buckets, edge functions, realtime subscriptions, indexes, and triggers. The generator creates a Supabase project via the Management API, links it with the CLI, and applies migrations. If deployment fails, an error classifier maps the failure to a pre-authored remediation taxonomy; Laya selects the relevant resolution MCQ, the user chooses, the specification is updated, and the build retries up to a bounded number of attempts. If the error cannot be resolved automatically, it is escalated to human review. On success, the project URL and API keys are returned.

In short, we chose this architecture because correctness comes from deterministic structure and targeted human confirmation, not from unconstrained generation. Laya is a small, replaceable decision component. The core of the system is the ontology, the constraint graph, the MCQ orchestration, the composition engine, the Supabase generator, and the test suite. The workflow is: interpret → classify → clarify → specify → validate → approve → compile → deploy → remediate → retry. That is the architecture we arrived at after rejecting pure LLM generation, Laya-as-extractor, pure rule-based parsing, and direct text-to-SQL, and after accepting that the intelligence must live in the ontology and templates we author, not in the model alone.
